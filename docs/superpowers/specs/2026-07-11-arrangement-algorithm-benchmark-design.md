## 一、背景与目标

本实验旨在对 NTEZMusic 项目中已有的多种 88 键到 36 键编曲压缩算法进行严格、可复现的横向基准评测。当前项目已积累七种编曲模式（`none`、`octave_fold`、`adaptive_octave_fold`、`hands_decoupled`、`attention_weighted`、`score_aware_theory`、`svsep_mpdr`），但缺乏统一的量化基准来衡量各算法在保真度、可玩性和听感三个维度上的相对表现。不同模式的设计理念差异显著，各自擅长的场景和短板不明确，导致算法选型与实际使用缺乏数据支撑。

**实验目标**：

1. 以"原曲保真度优先"为第一准则，通过统一的输入和指标体系横向对比所有正式候选算法。
2. 通过客观指标排序筛出前两名算法，再通过匿名 A/B 盲听确认主观听感差异。
3. 输出一份仅针对本基准所涉两首测试曲目的排名结论，不泛化到所有曲目类型。

## 二、核心理念与设计原则

### 2.1 原曲保真度优先

本基准的第一排序准则为"原曲保真度优先"。所有算法的得分计算中，衡量与原曲接近程度的指标（旋律轮廓、和声色度、节奏起音、低音骨架等）占据全部权重。游戏可弹性作为硬性门槛单独校验，不参与加权计分。

### 2.2 公平比较原则

1. **相同输入**：所有算法共享同一份原始 Transkun 转录 MIDI，不因算法差异而使用不同转录源。
2. **固定参数**：所有算法使用统一预设参数集（方案 A 固定默认值），不针对个别曲目或算法调参。
3. **相同渲染**：所有结果的音频回放使用同一声源和同一渲染流程，确保听感差异仅来自编曲算法本身。
4. **真实执行**：不使用 mock、stub、正弦合成或任何形式的伪造结果。所有指标必须基于真实编曲输出计算。

### 2.3 结论边界

本基准的结论严格限定于所测试的两首曲目，不得泛化为"算法 X 在所有曲目上优于算法 Y"。任何对外陈述均需注明"基于本基准两首测试曲目"的限定条件。

### 3.3 BPM 检测与记录

两首曲目的音频文件均不携带人工预设 BPM。在实验执行时，BPM 通过 librosa onset 检测从原始 MP3 音频中自动获取，检测结果记录为独立的 sidecar 配置值。

**关键规则**：BPM 检测值仅作为编曲算法的输入参数和输出 YAML 中的 tempo 元数据使用。**严禁**在 Transkun 原始转录 MIDI 内调用 `_fix_midi_tempo` 或任何其他方式改写该 MIDI 的 tempo 轨道、ticks 或时间信息。Transkun 输出的 MIDI 字节流保持不变。若某算法需要 BPM 信息，应从 sidecar 配置中读取，而非从 MIDI 文件中解析被篡改的 tempo 事件。

### 3.4 不可变原始 MIDI

**关键规则**：每首曲目生成一份且仅一份"基准 MIDI"，作为所有算法共用的不可变输入。

生成流程：

```
原始音频 (MP3)
  -> Demucs (htdemucs_6s) 分轨提取钢琴 stem
  -> Transkun (v2, 固定 checkpoint, 固定 segment 参数) 转录为 MIDI
  -> 输出：基准 MIDI (不可变，含原始 tempo/ticks)
```

具体约束：

1. **Demucs**：固定模型 `htdemucs_6s`，固定 stem 为 `piano`，不进行额外后处理。
2. **Transkun**：固定 checkpoint 路径、固定推理设备（CPU 或 CUDA，取决于执行环境一致选定）、固定 segment 参数（尺寸与步长均使用模型默认值，不指定时即用内置默认）。
3. **BPM**：通过 librosa 从原始 MP3 音频中检测，记录为 sidecar 配置值。检测出的 BPM **不写入**基准 MIDI 的 tempo 轨道。基准 MIDI 保留 Transkun 输出的原始 tempo 和 ticks。
4. **不可变性**：基准 MIDI 生成后，在后续所有算法运行中保持只读，不得因任何算法的预处理需求而修改。若某算法需要额外预处理（如量化、过滤），必须在算法内部自行完成，且预处理后的 MIDI 不得替代基准 MIDI。

每首曲目对应的基准 MIDI 存放于：

|------|---------------|
| `cruel_angel` | `work/arrangement_benchmark_20260711/cruel_angel/reference/base_midi/song.mid` |

## 四、算法候选与就绪门槛

### 4.1 正式候选算法

本基准纳入以下五种算法作为正式横向对比候选：

| 编号 | 模式名称 | CLI 参数值 | 简要特征 |
|------|----------|-----------|----------|
| C1 | 逐音八度折叠 | `octave_fold` | 逐音独立八度折叠，最简洁的暴力映射 |
| C2 | 自适应八度折叠 | `adaptive_octave_fold` | 以和弦为单位统一折叠系数 k，辅以 ref_pitch 平滑 |
| C3 | 左右手解耦折叠 | `hands_decoupled` | 左右手分离 + 三重交叉验证 + 和声功能简化 |
| C4 | 交叉注意力加权折叠 | `attention_weighted` | 小节滑动窗口 + 交叉注意力评分 + velocity 加权 + 精排管线 |
| C5 | SVSEP-MPDR 音频管线 | `svsep_mpdr` | AI 声部分离 + 主旋律 DP 跟踪 + MPDR 密度感知精排 |

### 4.2 非正式候选 / 参考基准

| 编号 | 模式名称 | CLI 参数值 | 定位 |
|------|----------|-----------|------|
| R0 | 原始 88 键基准 MIDI | 不调用压缩模式 | 作为保真度参考，不参与排名 |

R0 直接使用不可变的 Transkun 原始 B MIDI，不调用 `none` 生成 YAML，也不执行理论映射。`none` 无法满足 C3-B5 硬约束，因此不作为候选算法运行。

### 4.3 `score_aware_theory` 的就绪门槛

`score_aware_theory` 模式因涉及 MusicXML 合规化、乐理角色分析和更复杂的语义缩编逻辑，在纳入本基准前需通过以下就绪门槛：

1. **真实端到端运行**：必须在两首曲目上均完成一次完整的端到端运行（接收基准 MIDI 作为输入，产出 36 键 YAML 作为输出），不使用 mock 或占位逻辑。
2. **非空、可重读输出**：两首曲目的输出 YAML 均不得为空（文件大小 > 0，可被 YAML 解析器成功加载并重新读取），不设置最小音符数阈值。
3. **硬性门槛全通过**：输出的 YAML 必须通过本文档第六章定义的全部硬性约束（音域、和弦密度、输出格式、无重复 token、无时间反转、无非法事件、可重新读取）。

就绪门槛在实验执行阶段先行评估。**不存在任意相似度阈值**（如 MFCC 与其他算法的对比阈值）。若通过全部三项就绪门槛，`score_aware_theory` 以编号 C6 加入正式候选；若未通过，记录未通过原因并在最终报告中单独说明。

### 4.4 候选算法排除规则

以下情况将导致算法被排除出最终排名：

1. 算法在任何一首曲目上运行失败（报错退出）且无法通过不改变算法逻辑的方式修复。
2. 算法在任何一首曲目上输出空 YAML（文件大小为零或解析后无 score 事件）。
3. 算法在处理过程中引入了 mock 数据、伪成功状态或静默降级。

排除的算法在最终报告中被标记为"未完成"，不计入排名，但会记录其失败原因。

## 五、固定参数公平性方案

所有算法采用统一的方案 A 固定默认参数。禁止针对个别曲目或个别算法进行参数调优。

**集中化配置原则**：本文档声明的所有数值型实验设置（量化步长、最大和弦音数、最大事件数等）在实验执行时必须从一份集中的 manifest/配置文件读取，不得在实现代码中硬编码。若本文档与 manifest 配置文件存在不一致，以本文档为权威来源，但 manifest 配置文件必须与本文档保持一致后方可开始执行。

### 5.1 通用参数（所有候选统一）

| 参数 | 固定值 | 说明 |
|------|--------|------|
| `--beat-unit` | 4 | 节拍单位 |
| `--start-delay-seconds` | 3.0 | 弹奏前等待秒数（仅影响 YAML 元数据，不影响编曲逻辑） |
| `--key-press-seconds` | 0.0 | 按键保持秒数，播放层保底 1ms |

- 内置 36 键折叠范围固定为 C3-B5。
- 内置最大和弦音数固定为 6。
- 内部量化步长固定为 0.25 拍。
- 内部主旋律 DP 跟踪不使用视频辅助（纯音频主链路）。

## 六、硬性约束

所有算法的 36 键输出必须满足以下硬性约束。不满足的算法将被标记为不合格并排除出排名。硬性约束不设部分得分或降级通道，任一项不通过即排除。

### 6.1 音域约束

| 约束项 | 值 | 说明 |
|--------|-----|------|
| 最小可弹奏音高 | C3 (MIDI 48) | 低于此音高的音符必须被折叠或丢弃 |
| 最大可弹奏音高 | B5 (MIDI 83) | 高于此音高的音符必须被折叠或丢弃 |
| 目标音域跨度 | 3 个八度 (36 键) | 与《异环》游戏键盘布局一致 |

验证方式：解析输出的 YAML，逐事件检查最终 pitch 值是否全部落在 [48, 83] 区间内。

### 6.2 和弦密度约束

| 约束项 | 值 |
|--------|-----|
| 最大同时发音数 | 6 |

验证方式：解析输出的 YAML，逐和弦检查数组长度是否不超过 6。

### 6.3 输出格式约束

| 约束项 | 要求 |
|--------|------|
| 文件格式 | 合法的 YAML，顶层包含 `song`、`playback`、`keyboard`、`score`；`song` 内包含 `name`、`bpm`、`beat_unit` |
| token 类型 | 仅限项目 YAML 分数格式支持的合法 token（数字、半音修饰符、和弦数组） |
| 可解析性 | YAML 文件可被 `piano_auto_player.py` 成功加载并解析 |

### 6.4 数据完整性约束

| 约束项 | 要求 |
|--------|------|
| 无重复 token | 同一时间点不得出现重复 pitch 的 token（如 `[60 60]`） |
| 合法事件时值 | 每个 score 事件的 `beat` 表示该事件持续拍数，必须是有限正数；按事件顺序累加后绝对拍点必须严格递增 |
| 无非法事件 | 每个 token 必须是合法 MIDI pitch 值或修饰符，不得出现未定义符号 |
| 可重新读取 | 输出的 YAML 文件必须能被再次读取和解析，不得包含损坏或截断的数据 |

缩编 MIDI 还必须满足：所有音符使用实验配置声明的统一 velocity、不得包含 pedal/sustain 控制事件，并保留 YAML `beat` 所表达的事件持续时间。

### 6.5 产出物完整性约束

| 约束项 | 要求 |
|--------|------|
| YAML | 每个算法对每首曲目必须生成一个非空 YAML 文件 |
| 反解 MIDI | 每个 YAML 必须可反解为 MIDI 文件 |
| WAV | 每个缩编结果必须渲染出 WAV 文件 |
| MP3 | 每个缩编结果必须从 WAV 转码出 MP3 文件 |

验证方式：执行后检查指定路径下所有文件是否存在且可正常读取（不要求字节级校验，但要求文件大小 > 0 且格式头合法）。

## 七、保真度指标体系与权重

### 7.1 指标体系总览

本基准使用六项加权维度进行客观评分。游戏可弹性不设独立维度或指标表格——其全部要求已包含在第六章硬性约束中（C3-B5、最大六音同时发音、缩编 MIDI 无 pedal、统一 velocity、无重复 token/时间反转/非法事件、产出物完整可重读）。任一硬性约束未通过即排除候选算法出排名，不存在"可弹性未达标但保留排名资格"的降级通道。

| 维度编号 | 维度名称 | 权重 | 核心评估内容 |
|----------|----------|------|------------|
| D1 | 旋律音高与轮廓保真度 | 25% | 主旋律音符的 pitch 序列和音高轮廓在缩编后是否得到保留 |
| D2 | 和声/色度保真度 | 20% | 缩编后音频的 12 维色度向量与原始 88 键参考音频的相似度 |
| D3 | 起音/节奏保真度 | 20% | 音符 onset 时间点在缩编后是否与原始 MIDI 保持对齐，节奏骨架是否完整 |
| D4 | 低音骨架保真度 | 15% | 每小节或每拍的低音锚点 pitch 序列在缩编后是否保留 |
| D5 | 声部引导与音区层次 | 10% | 缩编后的音符在 C3-B5 音区内是否保持了原始声部的相对高低关系和层次 |
| D6 | 同源 WAV 音频特征相似度 | 10% | 原始 88 键渲染 WAV 与缩编 36 键渲染 WAV 之间的听感特征相似度（MFCC 或等效） |

**总分公式**：

```
总分 = D1×0.25 + D2×0.20 + D3×0.20 + D4×0.15 + D5×0.10 + D6×0.10
```

### 7.2 指标详细计算说明

#### D1: 旋律音高与轮廓保真度（25%）

1. 从原始 88 键基准 MIDI 中，通过 MPDR 主旋律 DP 路径提取主旋律音符序列。
2. 将主旋律音符映射到 36 键音域（C3-B5），超出部分按八度折叠处理，生成"期望旋律序列"。
3. 在缩编后的 36 键 MIDI 中，查找期望旋律序列中每个音符在对应时间窗口内是否有匹配（允许上下八度容差，时间容差为 +- 量化步长）。
4. 音高保留率 = 音高匹配的音符数 / 期望旋律序列音符数。
5. 轮廓保真度：计算期望旋律序列的相邻音高差向量（semitones），与缩编结果中匹配音符的相邻音高差向量之间的皮尔逊相关系数。
6. D1 = 0.6 × 音高保留率 + 0.4 × 轮廓保真度。输出范围：[0, 1]。

#### D2: 和声/色度保真度（20%）

1. 将原始 88 键基准 MIDI 通过原始渲染管线（保留 velocity、duration、pedal）渲染为 WAV 参考音频。
2. 将缩编后的 36 键 MIDI 通过缩编渲染管线（统一 velocity、无 pedal）渲染为 WAV 缩编音频。
3. 对两段 WAV 音频以 100ms 为帧长提取 12 维色度特征。
4. 计算全曲时间轴上的逐帧余弦相似度，取平均值。
5. 输出范围：[0, 1]，1 为完全一致。

#### D3: 起音/节奏保真度（20%）

1. 从原始 88 键基准 MIDI 中提取所有音符的 onset 时间（以拍为单位）。
2. 从缩编后 36 键 MIDI 中以相同方式提取 onset 序列。
3. 将两段 onset 序列量化为 0.25 拍网格（与量化步长一致），构建 onset 密度向量（每网格单元中是否有音符）。
4. 计算两段 onset 密度向量的 F1 分数（精确率与召回率的调和平均）。
5. 输出范围：[0, 1]，1 表示所有原始 onset 点均在缩编后得到保留且无冗余。

#### D4: 低音骨架保真度（15%）

1. 从原始 88 键基准 MIDI 中，以拍为单位（每 0.25 拍为一个网格）提取每个时间窗内的最低音 pitch。
2. 在缩编后的 36 键 MIDI 中查找对应时间窗的最低音 pitch（允许上下八度容差）。
3. 低音锚点保留率 = 匹配的拍数 / 有音符的总拍数。
4. 计算两段低音 pitch 序列的编辑距离（Levenshtein），归一化到 [0, 1]。
5. D4 = 0.5 × 保留率 + 0.5 × (1 - 归一化编辑距离)。输出范围：[0, 1]。

#### D5: 声部引导与音区层次（10%）

1. 从原始 88 键基准 MIDI 中，提取同时发音的音符组（和弦事件）的 pitch 分布。
2. 在缩编后 36 键 MIDI 的对应和弦事件中，校验以下保留情况：
   - 原始和弦的最高音和最低音在缩编后是否仍为相对最高和最低。
   - 原始和弦内 pitch 多元组的排序在缩编后是否被打乱（Kendall tau 距离）。
3. D5 = 0.5 × 极端音保留率 + 0.5 × (1 - 归一化排序距离)。输出范围：[0, 1]。

#### D6: 同源 WAV 音频特征相似度（10%）

1. 使用与 D2 相同的两段 WAV 渲染音频（原始 88 键 vs 缩编 36 键）。
2. 对两段 WAV 以 100ms 帧长提取 20 维 MFCC 特征。
3. 计算全曲时间轴上的逐帧余弦相似度，取平均值。
4. 输出范围：[0, 1]，1 为完全一致。

### 7.3 可弹性约束（已合并至第六章硬性约束）

游戏可弹性在本基准中不作为独立维度或独立门槛表格存在。所有可弹性相关约束已合并至第六章硬性约束，具体为：

- 音域 C3-B5（6.1）
- 最大六音同时发音（6.2）
- 缩编渲染 MIDI 无 pedal（见第十章渲染方案）
- 缩编渲染 MIDI 统一 velocity（见第十章渲染方案）
- 无重复 token / 无时间反转 / 无非法事件 / 可重新读取（6.4）
- 产出物完整可重读（6.5）

上述硬性约束均为**排除性门槛**：任一项不通过，候选算法即被排除出排名，不存在"记录但不影响排名"的降级处理。

### 7.4 指标计算约束

- 所有指标必须从基准 MIDI（不可变）和缩编后 YAML 反解 MIDI 的真实数据计算，不依赖 mock 数据或预设值。
- 所有中间计算结果可追溯，输出到每曲目各自的指标日志文件中。
- 若某项指标因依赖的工具或模块不可用而无法计算，**立即停止实验并报告失败**。严禁将该项指标设为零、默认值或跳过验证。
- D2 和 D6 的音频特征计算必须使用 **WAV** 格式的渲染音频，不得使用 MP3（MP3 仅用于盲听分发和归档）。

## 九、主观盲听确认流程

### 9.1 盲听目的

客观指标排名可能存在"高分低听"的情况（即指标得分高但主观听感不佳）。盲听阶段用于对客观排名前两名的结果进行主观听觉验证。

### 9.2 盲听设计

1. **匿名化**：将前两名算法在每首曲目上的渲染 WAV 文件以随机字母代号命名（如 `alpha.wav` 和 `beta.wav`），代号与算法的映射关系记录在密封文件中。
2. **包括原始参考**：引入原始 88 键渲染 WAV 作为"上界参考"，但不参与投票。
3. **A/B 评选**：听者同时获得当前曲目的原始参考音频和两个匿名缩编音频，要求回答：
   - 哪一个缩编版本更接近原始参考的听感？（A 更优 / B 更优 / 无明显差异）
   - 用一句话描述两个版本最主要的差异点。
4. **两曲独立**：两首曲目各自独立盲听，不交叉比较。
5. **记录**：每位听者的选择与描述记录在盲听日志中。

### 9.3 盲听结果处理

- 若多数听者（>= 50%）的偏好与客观排名一致，则客观排名得到主观确认，在最终报告中标注"客观与主观一致"。
- 若多数听者的偏好与客观排名相反，则在最终报告中**同时报告客观排名第一与盲听偏好第一**，注明两首曲目各自的客观得分和盲听偏好结论，由用户最终决定哪个算法更优。**不合成"单一赢家"**。
- 若听者无法区分差异（>= 50% 选择"无明显差异"），则最终报告中注明"主观听感差异不显著"，以客观排名为准。

### 9.4 盲听参与要求

- 最少参与人数：1 人（至少为项目作者本人）。
- 听音设备：统一使用同一副监听耳机或监听音箱。
- 听音环境：安静室内环境。
- 不允许在盲听过程中查看代号映射或指标数据。

## 十、音频渲染方案

### 10.1 渲染管线

所有音频渲染使用 FluidSynth 作为 MIDI 合成引擎。渲染分两路：

**原始参考渲染（88 键）**：

- 输入：基准 MIDI（不可变）
- SoundFont：一份经过许可证验证的真实采样大钢琴 SoundFont（同下方缩编渲染）
- 保留项：原始 velocity、原始 duration、原始 pedal（sustain）事件
- 输出：WAV → ffmpeg 转 MP3

**缩编结果渲染（36 键）**：

- 输入：YAML 反解后的 36 键 MIDI
- SoundFont：同上
- 强制项：
  - 所有音符使用实验集中配置中的统一 `reduced_velocity`，该值写入 manifest，禁止在实现代码中硬编码
  - 音符 duration 由 YAML 事件的 `beat` 按歌曲 BPM 换算，不额外改写为固定毫秒值
  - 无 pedal（sustain）事件
  - 音域严格限定在 C3-B5（MIDI 48-83）
  - 同时发音数不超过 6
- 输出：WAV → ffmpeg 转 MP3

缩编渲染的强制参数用于消除 velocity 和 sustain 差异对听感对比的干扰，确保听感差异仅来自音符选择本身。

### 10.2 SoundFont 选择

**唯一 SoundFont**（用于指标计算与盲听）：

- 类型：真实采样大钢琴 SoundFont
- 要求：至少 3 层力度采样，立体声，44.1kHz 或 48kHz，16-bit 或 24-bit
- 来源：需通过音源合规预检（见第十一章）确认其可用于本实验
- 不设备用 SoundFont；若主 SoundFont 不合规，必须找到合规替代品后方可继续

### 10.3 渲染命令

SoundFont 渲染 WAV：

```
fluidsynth -ni <soundfont_path> -F <output_wav> -r 44100 <input_mid>
```

WAV 转 MP3：

```
ffmpeg -i <input_wav> -codec:a libmp3lame -b:a 320k <output_mp3>
```

### 10.4 渲染文件命名与存放

| 类别 | 命名模式 | 示例 |
|------|---------|------|
| 原始参考 WAV | `<slug>_reference.wav` | `cruel_angel_reference.wav` |
| 原始参考 MP3 | `<slug>_reference.mp3` | `cruel_angel_reference.mp3` |
| 缩编渲染 WAV | `<slug>_<算法缩写>_reduced.wav` | `cruel_angel_C4_reduced.wav` |
| 缩编渲染 MP3 | `<slug>_<算法缩写>_reduced.mp3` | `cruel_angel_C4_reduced.mp3` |

### 10.5 客观指标计算专用格式

D2 和 D6 的音频特征提取一律使用 WAV 格式的渲染音频。MP3 有损压缩引入的编解码差异不得混入客观指标计算，MP3 仅用于盲听分发和归档。

## 十一、音源合规预检

### 11.1 预检目的

在实验执行阶段的第一步，必须对拟使用的 SoundFont 进行合规性校验，确保其许可协议允许在本实验中使用（包括渲染、公开分发渲染音频文件和实验报告中的频谱图引用）。

### 11.2 预检内容

1. **来源确认**：记录 SoundFont 文件的精确来源 URL 或购买渠道。
2. **许可解读**：阅读并记录 SoundFont 的许可证全文，提取与本实验使用场景相关的条款。
3. **使用判定**：逐项判定以下使用场景是否被许可：
   - 使用该 SoundFont 渲染 MIDI 为 WAV/MP3 音频文件。
   - 在实验报告中引用渲染音频片段（时长 <= 30 秒）作为示例。
   - 在实验报告中展示渲染音频的频谱图或波形图作为可视化证据。
4. **判定结果**：汇总为"通过 / 有条件通过 / 不通过"三种结论。
   - 通过：所有场景均被明确允许或未被禁止。
   - 有条件通过：部分场景需要注明出处或遵守特定限制。
   - 不通过：任一必需场景被明确禁止。

### 11.3 不通过的处理

若 SoundFont 未通过合规预检，实验**不得继续执行**。需要寻找替代 SoundFont 并重新进行预检，直至找到通过合规预检的音源。不存在自动降级到备用 SoundFont 的路径。

## 十四、失败处理策略

### 14.1 算法运行失败

若某个算法在任何一首曲目上运行失败（Python 异常退出或返回非零退出码）：

1. 记录完整的标准输出、标准错误和异常堆栈到 `run.log`。
2. 将算法状态标记为 `failed`。
3. 不尝试通过修改算法逻辑来修复，仅记录失败原因。
4. 在最终排名中标记为"未完成"，不计分。

### 14.2 指标计算失败

若某项指标因依赖的工具或模块不可用而无法计算：

1. **立即停止实验**。不应继续执行后续步骤。
2. 在日志中详细记录失败的指标编号、依赖的工具/模块名称、具体错误信息。
3. 向用户报告阻断原因，等待问题解决后重新执行。
4. **严禁**将失败指标的得分设为 0、默认值或跳过该指标继续执行。实验要么全部指标可计算，要么不做。

### 14.3 渲染失败

若某个 WAV 或 MP3 文件渲染失败：

1. 立即停止依赖该渲染产物的后续步骤。
2. 记录失败原因。
3. 不尝试用简化合成（如正弦波）替代真实 SoundFont 渲染。

### 14.4 严禁的降级行为

以下行为在本实验中**严格禁止**：

- 用 sine 合成替代真实 SoundFont 渲染。
- 用 mock 数据填充缺失的指标值。
- 用默认值（如 0、1.0、0.5）填充无法计算的指标维度。
- 用人为主观判断替代客观指标计算。
- 跳过无法通过的硬性约束而仍标记算法为合格。
- 用算法 A 的结果伪装成算法 B 的结果。
- 在客观排名已确定后修改任何参数、数据或权重以改变排名。

## 十五、验收标准

本实验的设计阶段在以下条件全部满足时视为"已审批"，可进入执行阶段：

1. 本设计文档已由项目技术总监审阅并批准。
2. 指标体系与权重已确认（六维度加权 + 可弹性硬性门槛），不存在未解决的争议。
3. 算法候选列表已确认，就绪门槛标准已明确（`score_aware_theory` 端到端 + 非空 + 全硬性门槛通过）。
4. 音源合规预检流程已明确，不遗漏任何使用场景。
5. 产出物目录结构已确认，覆盖所有中间与最终输出。
6. 用户已明确发出"开始"指令，授权进入执行阶段。

执行阶段的验收标准：

1. 所有候选算法（除 `none` 外）均成功运行并输出合法 YAML，或被明确排除并记录原因。
2. 所有六项客观指标维度均已成功计算并记录明细。
3. 盲听阶段已完成并记录日志。
4. `manifest.json` 已生成并包含完整的校验和与依赖信息。
5. 最终报告 `final_report.md` 已撰写，完整呈现排名、指标明细、盲听结论与边界声明。
6. `soundfont_compliance_report.md` 已生成，音源使用已通过合规预检。

## 十六、明确排除项

以下内容不属于本实验范围：

1. **算法改进**：本实验仅评测现有算法，不修改任何算法逻辑。即使评测中暴露出算法缺陷，也不在本实验中修复。
2. **新算法开发**：不开发新的编曲算法。`score_aware_theory` 若未通过就绪门槛，仅记录原因，不进行开发。
3. **跨曲目泛化**：不基于两首曲目的结果推广到所有曲目类型。结论严格限定于本基准。
4. **游戏内弹奏验证**：不将 YAML 写入游戏并实际弹奏来验证。验证环节仅限于音频回放。
5. **性能评测**：不对比各算法的运行效率、内存占用或推理时间。如需性能数据，仅记录运行耗时作为参考信息，不计入排名权重。
6. **视频音画同步**：不评测算法在视频配乐场景下的表现。本实验仅测试纯音频输入场景。
7. **音色合成质量**：不评测 SoundFont 本身的音色质量。SoundFont 仅作为统一的渲染工具。
8. **自动弹奏系统**：不评测 `piano_auto_player.py` 的弹奏精度或延迟。本实验仅评测编曲算法本身。
9. **非钢琴乐器**：不测试吉他、管弦乐或其他非钢琴乐器的转录和编曲。两首测试曲目均为纯钢琴曲。
10. **实时性**：不测试算法的实时或流式处理能力。所有评测均为离线批处理。
