## 一、问题建模与对比

### 1.1 现有方法本质

当前四种模式（`none` / `octave_fold` / `adaptive_octave_fold` / `hands_decoupled`）的核心均属**规则驱动**：

| 维度 | 现有体系 | 本质 |
|------|---------|------|
| 音高折叠 | 统一 k 偏移 + ref_pitch 指数平滑 | 一维因果低通滤波 |
| 和弦简化 | 音程优先级查表（根音=0、三度=10、七度=15、五度=80） | 固定权重线性排序 |
| 左右手判定 | 双峰检测 + 运动模式 + velocity | 多信号投票，静态阈值 |
| 密度控制 | 一刀切 max_chord_notes + duration 加权 | 分段线性映射 |
| 全局一致性 | 双向指数平滑趋势线 | 非因果低通 + 插值 |

所有决策都是**局部贪心 + 人工硬编码参数**。没有跨时间片的联合推理。

### 1.2 Transformer 视角下的核心缺陷

将现有算法映射到注意力范式后，暴露出三个根本问题：

1. **全局注意力的"无关 token 强制耦合"**
   - 现有 ref_pitch 将全曲所有时间片的音高重心用一根指数平滑线串联
   - 前段高音区推高 ref_pitch → 后段低音被迫做不自然的上八度迁移
   - 等价于 Transformer 中所有 token 强制共享同一 attention head，没有做"无关 token 屏蔽"

2. **分段决策的"因果截断"**
   - `hands_decoupled` 在休止符处切段，每段独立计算分割线
   - 段与段之间信息隔离 → 同一个和弦进行（如 I-IV-V-I）在不同段中被不同策略裁剪
   - 等价于 self-attention 中强行把 attention mask 在段边界截断

3. **简化策略的"维度塌缩"**
   - 和声优先级查表只考虑了 pitch class 距离（3 半音 = 三度），忽略了 velocity、duration、前后和弦上下文
   - 等价于只用一个 attention head 且 query/key 的维度为 1（仅 pitch class）

## 二、Transformer 方案架构设计

### 2.1 总览：两阶段精排管线

```
阶段 1（规则候选生成 -- 现有系统，不改动）
  原始 MIDI → hands_decoupled 多参数变体 → K 个候选 YAML 曲谱
  ├── 候选 1: k=0 默认参数
  ├── 候选 2: 提高 left_max_chord_notes
  ├── 候选 3: 降低 ref_smoothing
  └── 候选 K: 不同参数组合

阶段 2（Transformer 精排 -- 新增模块）
  原始 MIDI 嵌入 + K 个候选嵌入 →
    ┌─ 全局交叉注意力 ─┐
    ├─ 段内交叉注意力 ─┤ → 候选质量评分 → 选择最优候选
    └─ 位置编码 ───────┘
```

**设计理由**：Transformer 不直接生成音符（避免 LLM 幻觉问题），而是作为**评分器**对规则系统生成的候选做精排。这保留了规则系统的确定性保底，同时在选优环节引入学习能力。

### 2.2 Token 化方案

**词汇表设计**（89 个 token）：

| Token ID | 含义 |
|----------|------|
| 0 | 休止符（rest），对应时间片无音符 |
| 1-88 | MIDI 音高 21-108（A0-C8，标准钢琴 88 键），直接用 pitch 值偏移 |

**序列表示**：按时间片排列的变长序列，每个时间片包含该拍所有活跃音符的 token 集合。表示为：

```
S = [(t₁, {p₁₁, p₁₂, ...}), (t₂, {p₂₁, ...}), ...]
```

其中 `tᵢ` 为量化后的时间片索引，可用于计算位置编码。

### 2.3 嵌入层设计

每个时间片通过三种嵌入叠加：

```
E(t, P_t) = E_note(P_t) + E_pos(t) + E_seg(t)
```

**音符嵌入 `E_note`**：
- 将时间片内音符的多热向量（89 维）通过线性投影映射到 d_model 维
- 或使用可学习的 note embedding table（89 × d_model），时间片嵌入取该片所有活跃音符嵌入的均值 + max pooling

**位置编码 `E_pos`**：
- 使用正弦位置编码，但将"位置"映射为**拍点值**而非整数索引
- 公式：`PE(beat, 2i) = sin(beat / 10000^(2i/d_model))`，`PE(beat, 2i+1) = cos(beat / 10000^(2i/d_model))`
- 其中 `beat = t × quantize_beat`，编码了绝对音乐时间
- 重要性：同一首曲子在 60 BPM 和 120 BPM 下的量化步长不同，使用实际拍点值保证泛化

**段嵌入 `E_seg`**：
- 复用现有 `_segment_by_gaps` 结果，为每个段分配一个可学习的 segment embedding（类似 BERT 的 segment embedding）
- 段内所有时间片共享同一个段嵌入
- 目的：让模型感知乐句边界

### 2.4 编码器：源序列自注意力

**输入**：原始 MIDI 的嵌入序列 `E_src ∈ ℝ^(T_src × d_model)`

**结构**：
```
E_src → [Multi-Head Self-Attention → FFN] × N_enc 层
```

- 自注意力捕捉长程音乐依赖：主题再现、和声进行、情绪递进
- Multi-head 同时关注不同音乐维度：
  - Head 1: 音高轮廓（旋律线走向）
  - Head 2: 和声密度（织体厚薄变化）
  - Head 3: 节奏模式（音符密度波动）
  - Head 4: 音区分布（全局音域重心迁移）

### 2.5 交叉注意力层（核心）

**2.5.1 全局交叉注意力**

```
Q = W_q × Z_target （压缩候选的嵌入）
K = W_k × E_src_encoded （源序列编码）
V = W_v × E_src_encoded

Attention(Q, K, V) = softmax(QK^T / √d_k) × V
```

- **Query（查询）**：可学习的"压缩查询向量"（类似 DETR 的 object queries），数量 = 每个时间片的最大输出槽位数（如 4 个，对应 max_chord_notes）
- **Key/Value（键值）**：来自源序列编码器的输出
- 直觉：每个压缩槽位"询问"原始 MIDI——"我应该保留哪个音符？"

**查询向量设计**：
- 不使用固定可学习查询，而是从规则候选的压缩结果中提取查询
- 候选 YAML 中每个时间片的 token 集合 → 嵌入 → 池化 → 作为该时间片的查询
- 这保证了查询本身包含了规则系统的先验知识

**2.5.2 段内交叉注意力**

在全局交叉注意力之后，对每个段单独再做一次交叉注意力：

```
对每个段 seg:
    Q_seg = segment_pooling(全局交叉注意力输出)
    K_seg, V_seg = 该段对应的源序列编码

    Output_seg = CrossAttention(Q_seg, K_seg, V_seg)
```

- **目的**：全局层决定"这首曲子的整体压缩策略"（如偏旋律保留还是偏和声保留），段内层微调"本乐句的具体音符选择"
- **段池化**：取段内所有时间片输出的均值 + 最大池化拼接
- **段边界处理**：段边界处 source key/value 加上段位置编码偏移（与段嵌入呼应）

### 2.6 输出头：候选质量评分

经过两层交叉注意力后，对每个候选 YAML 输出一个标量质量分：

```
score = MLP(concat(
    global_pooling(output),      # 全局特征
    harmonic_consistency,        # 和声一致性辅助特征
    voice_leading_smoothness,    # 声部进行平滑度辅助特征
    density_balance,             # 密度平衡辅助特征
    melodic_contour_similarity,  # 旋律轮廓保持度辅助特征
))
```

**辅助特征**（手工计算，非学习）：
- 和声一致性：相邻时间片和弦根音运动的平均半音距离
- 声部进行平滑度：相邻时间片各声部（最高音/最低音/次高音）的平均半音跳变
- 密度平衡：全曲音符密度分布的方差倒数
- 旋律轮廓保持度：候选与原始 MIDI 最高音轨迹的 DTW 距离

这些辅助特征作为"乐理先验"注入评分头，缓解训练数据不足的问题。

## 三、训练策略

### 3.1 核心挑战：无标注训练数据

我们没有"好压缩 / 坏压缩"的人工标注对。需要自监督或弱监督策略。

### 3.2 方案 A：对比学习（推荐）

**正例构造**：
- `hands_decoupled` 模式的输出（当前最佳规则系统）
- 对同一 MIDI 用不同的合理参数生成多个"可接受"的候选

**负例构造**：
- 随机丢弃 30%-50% 音符
- 纯 `octave_fold` 输出（无和弦简化，密度过高）
- 随机修改 k 偏移导致和弦内音程破坏
- 全部音高映射到同一八度的退化压缩

**损失函数**（InfoNCE）：

```
L = -log( exp(score_pos / τ) / Σ_i exp(score_i / τ) )
```

其中 τ 为温度参数，让模型学会将正例打分显著高于负例。

**数据增强**：
- 对同一 MIDI 做 ±1~6 半音的全局移调，生成增强样本
- 随机时间拉伸（改变 BPM，保持音高）
- 训练时 dropout 部分音符（模拟转录误差）

### 3.3 方案 B：知识蒸馏

- **教师**：`hands_decoupled` 规则系统（输出确定性的 token 序列）
- **学生**：Transformer 模型
- **目标**：Transformer 不仅学会规则系统的决策，还要学会"平滑化"——规则系统的硬阈值（如密度 cap 从 2 跳到 3）在 Transformer 中变为连续概率

**损失函数**：

```
L = L_CE(output, teacher_output) + λ × L_smooth
```

其中 `L_smooth` 惩罚相邻时间片输出 token 分布的 KL 散度（鼓励平滑过渡）。

### 3.4 方案 C：多目标乐理约束

不使用标注，定义一组可微分的乐理约束作为损失函数：

| 约束 | 公式 | 权重 | 说明 |
|------|------|------|------|
| 音程保持 | `Σ_t Σ_{i≠j} ∥interval(p_i,p_j) - interval(p'_i,p'_j)∥` | 0.4 | 和弦内音程不应被破坏 |
| 旋律完整性 | `DTW(top_line_orig, top_line_candidate)` | 0.3 | 最高音轨迹应保持 |
| 低音功能性 | `cos_sim(bass_motion_orig, bass_motion_candidate)` | 0.15 | 低音进行方向应一致 |
| 密度合理性 | `∥density - target_density∥²` | 0.1 | 密度不应爆炸或塌缩 |
| 声部进行 | `Σ_t ∥nearest_voice(p'_t, p'_{t-1})∥` | 0.05 | 相邻时间片最近声部跳变最小 |

**局限性**：需要大量 MIDI 数据才能使 Transformer 学到通用模式，单独几首曲目可能过拟合。

### 3.5 推荐训练组合

**Phase 1（预训练）**：在公开钢琴 MIDI 数据集上做自监督掩码重建（Masked Note Modeling）
- 随机掩码 15% 的音符，训练模型重建
- 类似 BERT 的 MLM，让模型学会钢琴音乐的统计规律

**Phase 2（蒸馏）**：使用知识蒸馏让模型逼近 `hands_decoupled` 的决策

**Phase 3（对比微调）**：用对比学习微调评分头，学会区分"好"和"差"的压缩

**Phase 4（在线自适应）**：对每首新曲目，用规则系统生成候选后，用 Transformer 精排

## 四、可行性评估

### 4.1 技术可行性

| 维度 | 评估 | 说明 |
|------|:---:|------|
| Token 化 | **高** | 89 token 词汇表，直映射 MIDI pitch → token ID，零歧义 |
| 位置编码 | **高** | 标准正弦编码，将时间片索引替换为拍点值，实现简单 |
| 段内交叉注意力 | **中高** | 技术可行，段嵌入 + 段内注意力 mask 实现直截了当 |
| 编码器自注意力 | **高** | 标准 Transformer encoder，复杂度 O(T²)，T≈2000 时间片，可接受（2000²=4M，单层 <100ms） |
| 交叉注意力 | **中** | 查询设计是关键难点——需要验证压缩查询向量是否具有足够的表达能力 |
| 端到端训练 | **低-中** | 缺乏标注数据是最大瓶颈；对比学习 + 知识蒸馏可绕过，但效果需要验证 |

### 4.2 实用可行性

| 维度 | 评估 | 说明 |
|------|:---:|------|
| 依赖增量 | **中** | 需引入 PyTorch（~800MB），当前 requirements.txt 不含 ML 框架 |
| 推理速度 | **中高** | 推理可纯 CPU，2 层 Transformer 处理 2000 时间片约 1-3 秒 |
| 训练资源 | **中** | 2-4 层 Transformer 可在单 GPU 上训练，或使用 doubao API 做嵌入（但非直接可用） |
| 代码改动量 | **中** | 新增 ~350 行 Transformer 模块，现有管线改动约 50 行（插入精排阶段） |
| 调试难度 | **中** | Transformer 的黑盒性使错误定位比规则系统困难；需要大量可视化工具 |

### 4.3 音乐可行性（能否比现有更好？）

| 场景 | 现有规则 | Transformer 预期 | 提升可能性 |
|------|---------|----------------|:---:|
| 清晰旋律+伴奏 | 表现优秀 | 持平或略优 | 低 |
| 交叉声部（左手副旋律） | 双峰检测可能误判 | 多头注意力可同时追踪多条线 | **中高** |
| 密集和弦（≥6 音） | 一刀切丢弃五度/八度 | 学习到的丢弃策略更平滑 | **中** |
| 音区突变段落 | ref_pitch 平滑延迟 | 全局自注意力可预判 | **中** |
| 非标准调性和声 | 固定音程优先级不适用 | Transformer 学习通用模式 | **低-中** |
| 纯音阶跑动（无和弦） | 表现优秀 | 持平 | 低 |
| 转调段落 | 趋势线跟随但可能有延迟 | 注意力直接关联远距离 token | **中** |

### 4.4 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|:---:|:---:|------|
| 训练数据不足导致模型退化为随机 | 高 | 高 | 先用知识蒸馏，保证不低于规则基线 |
| Transformer 输出破坏和弦音程 | 中 | 高 | 输出后处理加入统一 k 约束兜底 |
| 过拟合到训练曲目，新曲效果差 | 中 | 中 | 数据增强（移调、时延、音符 dropout）+ 大规模 MIDI 预训练 |
| 推理速度影响批处理体验 | 低 | 低 | 模型极小化（2 层、256 维），CPU 推理 |
| 段分割质量影响段内注意力 | 低 | 中 | 段嵌入仅作为辅助信号，段内注意力不做硬截断 |
| 输出音符超出键盘范围 | 低 | 高 | 输出映射层加入 soft clamp 约束 |

## 五、与现有方案的对比

| 维度 | `adaptive_octave_fold` | `hands_decoupled` | RD-DLAF（提案） | **Transformer 精排** |
|------|:---:|:---:|:---:|:---:|
| 范式 | 规则 | 规则 | 规则 | **学习 + 规则混合** |
| 注意力机制 | 单一 ref_pitch 因果平滑 | 双向趋势线 + 段内双峰 | 3 条独立因果 ref_pitch | **多头自注意力 + 交叉注意力** |
| 和弦简化 | 音高极值优先（一刀切） | 音程功能优先级查表 | 音程张力权重排序 | **学习到的注意力权重 + 乐理辅助特征** |
| 参数数量 | 1 个 | 7 个 | ~10 个 | **可学习参数（~2M）+ 5 个超参** |
| 跨时间片推理 | 因果单向，逐片独立决策 | 段内独立决策，段间信息隔离 | 因果逐轨，轨间碰撞消解 | **全局双向自注意力，长程依赖建模** |
| 确定性 | 完全确定 | 完全确定 | 完全确定 | **随机（训练）/ 确定（推理）** |
| 可解释性 | 高（直接映射） | 高（分段 + 双峰可见） | 高（三条 ref_pitch 轨迹可见） | **低（注意力权重可可视化但不可控）** |
| 泛化能力 | 弱（参数固定） | 中（段自适应但阈值固定） | 中（角色自适应但阈值固定） | **强（从数据中学习，可适应不同风格）** |
| 训练需求 | 无 | 无 | 无 | **需要 MIDI 数据 + GPU** |

## 六、推荐实施路径

### Phase 0：基础设施（1-2 天）

1. 引入 PyTorch（`pip install torch --index-url https://pypi.tuna.tsinghua.edu.cn/simple`）
2. 搭建最小 Transformer 模块框架（`src/transformer_reranker.py`）
   - Multi-Head Self-Attention
   - Cross-Attention
   - Positional Encoding（beat-based sinusoidal）
   - Segment Embedding

### Phase 1：数据管线（2-3 天）

1. MIDI → Token 序列转换器（`_midi_to_token_sequence`）
2. 规则系统多参数候选生成器（对现有 `hands_decoupled` 包裹参数扫描）
3. 辅助特征计算器（和声一致性、声部进行等）
4. 数据集构建：用项目现有的 9 首曲目 + 公开 MIDI 数据

### Phase 2：知识蒸馏训练（3-5 天）

1. 以 `hands_decoupled` 为教师，训练 Transformer 逼近其决策
2. 验证蒸馏后的模型是否至少不比教师差
3. 分析注意力权重，确认模型学到了有意义的音乐模式

### Phase 3：对比学习微调（2-3 天）

1. 构造正负例对
2. 微调评分头
3. A/B 测试：规则基线 vs Transformer 精排

### Phase 4：集成到现有管线（1-2 天）

1. 新增 `--rerank-mode transformer` CLI 参数
2. 在 `MidiToYamlConverter` 中加入 Transformer 精排阶段
3. 转换报告新增精排相关统计

### Phase 5：验证与对比（2-3 天）

1. 用全部 9 首曲目做留一法交叉验证
2. 人工听感评估
3. 量化指标对比（八度迁移率、和弦密度分布、旋律保持度）

## 七、核心判断

### Transformer 能否做到"更优美"？

**有条件地可以**，前提是：

1. **足够多的训练数据**（至少 50-100 首不同风格的钢琴 MIDI）
2. **合理的训练策略**（知识蒸馏 → 对比学习 → 在线精排）
3. **输出约束兜底**（Transformer 评分 + 规则系统生成，不直接生成音符）

纯端到端 Transformer 生成压缩结果在当前条件下**不可行**（无标注数据、输出空间巨大、和弦约束难保证）。

### Transformer 精排（二阶段）能否超越纯规则系统？

**在特定场景下可以**：

- 交叉声部、复杂和声、非标准调性的曲目 → Transformer 的多头注意力有优势
- 简单曲目（清晰旋律+伴奏）→ 持平，不会更差

### 和弦简化能否更合理？

**学习到的注意力权重替代固定优先级查表**，在理论上更合理——因为 Transformer 能够考虑：
- 前后和弦的延续性（一个七音在当前和弦是"色彩音"，在下一个和弦可能变成"准备音"，不应该丢弃）
- velocity 隐含的角色信息（力度强的音符更可能是旋律骨干，即使它不是最高音）
- duration 的时间权重（长音符承载和声骨架，短音符是装饰）

这些多维信息在固定查表中完全不可用。

### 结论

**Transformer 交叉注意力精排方案在技术上可行，在音乐上有提升空间，但训练数据是最大瓶颈。** 建议以"二阶段精排"（规则候选 + Transformer 评分）而非"端到端生成"作为实施方向，保留规则系统的确定性保底，同时引入 Transformer 的全局推理能力。

## 八、需要决策的问题

在进入实施前，需要确认：

1. **是否接受引入 PyTorch 依赖**？（约 800MB 安装体积）
2. **是否接受模型输出的非确定性**？（同一输入可能因随机种子产生不同评分排序，推理阶段可通过固定种子消除）
3. **训练数据范围**：仅用项目现有 9 首曲目（可能过拟合），还是采集公开 MIDI 数据集？
4. **优先目标**：和弦简化优化、旋律保持度、还是整体听感？
5. **是否允许使用 doubao API 做嵌入**？可用于替代本地训练的编码器，但需评估延迟和成本
