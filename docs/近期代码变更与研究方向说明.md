## 二、新增核心管线：乐谱语义感知缩编

### 2.1 设计动机

现有 `attention_weighted` 和 `svsep_mpdr` 两种主要缩编策略虽然实现了可用的 88→36 键压缩，但存在以下根本局限：

1. **缺乏乐谱语义层**：所有策略直接基于 MIDI 数值（音高列表 + velocity + 起音时间）做评分和筛选，不理解"这是主旋律还是伴奏"、"这段是什么和声功能"、"乐句边界在哪"。
2. **机翻 MIDI 噪声**：Transkun 转录的 MIDI 存在起音抖动、时值偏差、和弦聚合不精确等问题，直接输入压缩算法会放大误差。
3. **不可审计**：输出结果无法导出为标准乐谱格式（MusicXML），人工审查只能靠听觉。
4. **调性盲区**：`attention_weighted` 文档已明确指出缺少调性检测，所有音高被近似平等处理。

### 2.2 核心设计理念

新管线 `score_aware_theory` 的核心哲学是：

```text
MIDI 不是五线谱。五线谱需要小节、声部、调号、拼写、休止符、连音线等语义结构。
因此不能直接从 MIDI 压缩，而应先重建合规五线谱语义层，再基于语义做缩编。
```

### 2.4 关键设计决策

#### 记谱硬约束（7 条，不可协商）

1. 每个小节的总时值必须等于拍号容量
2. 每个声部内部不允许非法重叠
3. 空白时间必须由休止符补齐
4. 跨小节长音必须拆分并使用连音线表达
5. 音符时值必须落在允许集合中
6. MusicXML 必须可以成功导出并回读
7. 输出到 36 键之前必须保留原始 MIDI 对齐关系

#### 乐理软约束（7 条，用于评分和候选选择）

1. 旋律线应尽量连续
2. 低音骨架应尽量稳定
3. 和弦拼写应符合调性
4. 临时记号不应过度混乱
5. 乐句边界应靠近休止、长音、和声终止或小节周期
6. 声部之间不应频繁交叉
7. 缩编后应保留根音、三度、七度等关键和声信息

## 三、新增模块详解

### 3.1 数据模型：`src/score_model.py`

全管线共享的数据类定义，作为各模块之间的"合约语言"。核心类型包括：

| 类名 | 职责 |
|------|------|
| `CanonicalNote` | 清洗后的规范化音符（pitch, onset, duration, velocity） |
| `CanonicalizationConfig` | MIDI 清洗参数（sustain_threshold, noise_duration_min 等） |
| `CanonicalizationResult` | 清洗阶段输出（notes 列表 + 统计信息） |
| `BeatGrid` | 节拍网格（beats, measures, time_signature） |
| `QuantizedScore` | 量化后乐谱（notes 分配到 measures/voices/staves） |
| `StaffNotationConfig` | 五线谱构建配置 |
| `StaffNotationBuildResult` | 五线谱构建输出（是否成功、MusicXML 路径、诊断信息） |
| `SemanticAnalysisResult` | 语义分析输出（melody_notes, bass_notes, chords, phrases, voice_crossings） |
| `ArrangementConfig` | 36 键编排配置（key_range, max_chord_notes, priority_weights） |
| `ArrangementResult` | 编排结果（retained_notes, dropped_notes, quality_report） |
| `ScoreAwareTheoryConfig` | 总装管线配置（聚合各阶段参数） |

### 3.2 MIDI 清洗：`src/midi_event_canonicalizer.py`

**核心类**：`MidiEventCanonicalizer`

**清洗策略**：
- **延音合并**：检测 sustain pedal 范围内的重叠音，合并为一个逻辑音符
- **噪声过滤**：丢弃时长过短或间隔过大的孤立事件
- **和弦聚类**：将起音时间在阈值内的音符归为同一和弦组

**输入**：原始 MIDI 文件路径
**输出**：`CanonicalizationResult`（包含清洗后的 `CanonicalNote` 列表）

### 3.3 节拍网格：`src/beat_grid_estimator.py`

**核心类**：`BeatGridEstimator`

**策略**：确定性方法。基于用户提供的 BPM 和拍号配置，计算等距节拍网格，而非从 MIDI 中推断（避免引入额外估计误差）。每个音符的起音和时值后续都量化到此网格上。

**输入**：`CanonicalNote` 列表 + BPM + 拍号
**输出**：`BeatGrid`（包含拍点位置、小节边界）

### 3.4 量化器：`src/score_quantizer.py`

**核心类**：`ScoreQuantizer`

**策略**：
- 将每个音符的起音取整到最近的网格拍点
- 将时值取整到最近的网格时值单位
- 基于音高范围自动分配声部（右手/左手谱表）

**输入**：`CanonicalNote` 列表 + `BeatGrid`
**输出**：`QuantizedScore`

### 3.5 MusicXML 五线谱构建：`src/staff_notation_builder.py`

**核心类**：`StaffNotationBuilder`

**实现方式**：基于 `music21` 库构建双谱表（右手高音谱表 + 左手低音谱表）的 `stream.Score` 对象，导出为标准 MusicXML 格式。

**关键处理**：
- 强制执行记谱硬约束（小节时值完整性、声部不重叠、休止符补齐）
- 跨小节长音自动拆分 + 连音线标记
- 导出后回读验证（确保 MusicXML 可被其他工具正确解析）

**输入**：`QuantizedScore` + `StaffNotationConfig`
**输出**：`StaffNotationBuildResult` + `.xml` 文件

### 3.6 乐谱语义分析：`src/score_semantic_analyzer.py`

**核心类**：`ScoreSemanticAnalyzer`

这是整个管线中算法最密集的模块，负责从量化后的音符序列中提取音乐语义信息：

| 功能 | 方法/策略 | 用途 |
|------|---------|------|
| 主旋律线提取 | 基于音高轮廓 + 运动模式 + 最高音跟踪 | 确定哪些音符属于旋律线，缩编时优先保留 |
| 低音骨架识别 | 跟踪每个和弦时刻的最低音，保持连续性 | 确保和声根音不被丢弃 |
| 和声功能推断 | 基于同时发声的音符集合推断和弦根音与性质 | 用于和声填充的优先级排序 |
| 乐句边界检测 | 基于休止符、长音、和声终止、小节周期 | 提供乐句级上下文，辅助取舍决策 |
| 声部交叉检测 | 检测左右手的音区交叉 | 标记需要特殊处理的段落 |

**输入**：`QuantizedScore`
**输出**：`SemanticAnalysisResult`

### 3.7 36 键乐理缩编：`src/theory_aware_36key_arranger.py`

**核心类**：`TheoryAware36KeyArranger`

**选择策略**（按优先级排序）：

1. **主旋律线**（最高优先级）：旋律音符无条件保留，超出 36 键范围的做八度折叠
2. **低音骨架**：保留每个和声位置的最低音，维持和声根音支撑
3. **和声填充**：按乐理重要性排序
   - 根音 (root) — 最高优先级
   - 三度 (third) — 决定大小调性质
   - 七度 (seventh) — 决定属/下属等色彩
   - 五度 (fifth) — 最可丢弃（与根音泛音列重合度高）
4. **声部独立处理**：左右手分别约束，避免声部交叉

**约束条件**：
- 键盘范围：MIDI 48-83 (C3-B5)
- 单和弦最大音数：由 `max_chord_notes` 控制（默认 6）
- 左手最大和弦音数：由 `left_max_chord_notes` 控制（默认 2-3）

**输入**：`QuantizedScore` + `SemanticAnalysisResult` + `ArrangementConfig`
**输出**：`ArrangementResult`

### 3.8 总装管线：`src/score_aware_theory_pipeline.py`

**核心类**：`ScoreAwareTheoryPipeline`

对外暴露的单一入口，依次调用上述各阶段模块：

```python
result = pipeline.run(midi_path, config)
# 内部执行:
#   1. 清洗 -> 2. 网格 -> 3. 量化 -> 4. MusicXML -> 5. 语义 -> 6. 缩编
```

### 3.9 记谱验证器：`src/score_notation_validator.py`

独立的验证模块，在 MusicXML 构建后执行合规检查：
- 小节时值完整性
- 声部内重叠检测
- MusicXML schema 合规性

### 3.10 与 `audio_to_yaml_converter.py` 的集成

在主入口文件中新增了 `score_aware_theory` 压缩模式。集成方式：

- 新增 `_build_score_aware_theory_score_events()` 方法，作为该模式的入口
- 在模式验证列表中添加 `score_aware_theory`
- CLI 参数新增 `--pitch-compression-mode score_aware_theory` 选项
- 中间产物（MusicXML、审计报告）输出到 `--work-dir` 目录

## 四、与现有压缩模式的关系

### 4.1 模式全景对比

| 维度 | attention_weighted | svsep_mpdr | score_aware_theory |
|------|-------------------|-----------|-------------------|
| **核心思路** | 交叉注意力评分 + velocity 加权精排 | GNN 声部分离 + 多阶段精排 | 乐谱语义重建 + 乐理规则缩编 |
| **输入** | 转录 MIDI 原始事件 | 转录 MIDI + GNN 声部标注 | 转录/用户 MIDI（清洗后） |
| **语义层** | 无（直接操作音高列表） | 部分（GNN 声部标注） | 完整（小节/声部/和声/乐句） |
| **中间产物** | 评分日志 | GNN 分离结果 + 精排日志 | MusicXML + 语义分析报告 |
| **可审计性** | 弱（仅数字指标） | 中（有精排日志） | 强（MusicXML 可视化 + 审计报告） |
| **调性感知** | 无 | 无 | 计划中（和声功能推断已实现） |
| **缩编依据** | 注意力分数 + velocity | 声部归属 + 多维度评分 | 旋律/低音/和声功能优先级 |
| **复杂度** | 高（Transformer 交叉注意力） | 极高（GNN + 多阶段管线） | 高（多阶段语义管线） |
| **成熟度** | 生产可用 | 生产可用 | MVP 阶段 |

### 4.2 工程定位

`score_aware_theory` **不是替代现有模式**，而是在现有管线中新增一层：

```text
MIDI 输入
    │
    ├──→ attention_weighted ──→ YAML    （成熟，直接评分）
    ├──→ svsep_mpdr ──────────→ YAML    （成熟，GNN 声部辅助）
    │
    └──→ ScoreRegularizationLayer ──→ score_aware_theory ──→ YAML    （新增）
              │
              ├── MusicXML（可导出给人类审查）
              ├── 语义分析报告
              └── 乐理审计数据
```

### 4.3 与 MusicTheory 审查的关联

`docs/MusicTheory/` 目录下的 AUDIT.md 和 PLAN.md 是 `score_aware_theory` 模式的前置调研工作：

- **AUDIT.md**（2026-07-01）：对 `svsep_mpdr_v3` 三首曲目（One Last Kiss、ただ声一つ、残酷天使）进行了系统性乐理审查，识别出 6 类问题：
  1. 输入稳定性风险（同事件混合升降半音）
  2. 异常重音位置
  3. 和弦密度过高
  4. 节奏织体块状化
  5. 低音锚点疑似缺失
  6. 音区压缩过窄 / 节奏碎片化

- **PLAN.md**（2026-07-01）：基于审查结果制定的 8 任务 4 阶段改进方案，这些发现直接驱动了 `score_aware_theory` 的设计（尤其是记谱硬约束和乐理软约束的定义）。

## 六、Transkun 转录质量诊断与 Tempo 问题确认

> **重要性：极高**。此诊断结论改变了项目对"转录质量"的根本认知，直接影响到后续所有优化方向的选择。

### 6.1 背景：为什么需要诊断

在 2026-07-10 之前的评测中，项目一直使用 `_fix_midi_tempo()` 修改后的 MIDI（产物 C）与 MAESTRO 参考 MIDI（A）直接比对，得到 onset+pitch F1 仅约 0.05。这曾被解释为"Transkun 转录质量差、存在大量旋律错误"，并计划用乐理重排来修复。

但实际上，问题的根因完全不同。

### 6.2 A/B/C 产物定义与诊断方法

为避免混淆，诊断工作严格定义了三类不可变产物：

| 标识 | 产物 | 定义 |
|------|------|------|
| **A** | MAESTRO 参考 MIDI | 与真实录音配对的 Disklavier `reference_performance.midi` |
| **B** | Transkun 原始 MIDI | `model.transcribe()` 后由 `writeMidi()` 直接生成的 120 BPM MIDI，不调用 `_fix_midi_tempo()` |
| **C** | tempo 覆盖后 MIDI | 当前主管线产物，tempo 元事件被 librosa 检测值原地覆盖，音符 tick 未重算 |

此前项目从未保留 B，所有评测都基于被污染的 C。

### 6.3 核心发现

#### 1. B 与 C 的音符内容完全一致

经过逐事件对比（track、tick、message type、MIDI note、velocity、channel、事件顺序），B 与 C 的 **全部 note_on/note_off 事件完全相同**。唯一有效差异是 tempo 元事件：

```text
Bach:   500000 μs/beat → C: 510638 μs/beat  (约 117.5 BPM)
Chopin: 500000 μs/beat → C: 534283 μs/beat  (约 112.3 BPM)
```

结论：`_fix_midi_tempo()` 不改变旋律音高、不漏删音符、不改变 tick 节奏。它只修改了 MIDI 播放速度。

#### 2. B 的真实转录质量极高

| 指标 | 巴赫 BWV 846 | 肖邦 Op.10 No.12 |
|------|-------------:|-----------------:|
| onset+pitch F1 | **0.9950** | **0.9728** |
| onset+pitch+offset F1 | 0.9372 | 0.8400 |
| velocity-aware F1 | 0.9361 | 0.8270 |
| frame piano-roll accuracy | 0.9070 | 0.6811 |
| onset MAE | 3.41 ms | 4.71 ms |
| onset P95 | 8.07 ms | 11.72 ms |

**关键判断**：onset-only F1 与 onset+pitch F1 完全相同，说明成功检测到的起音几乎全部具有正确音高。不存在大规模半音错判、八度错判或谐波假音。

#### 3. C 的低 F1 来源于时间轴拉伸，不是旋律错误

C 的绝对时间被全局拉伸（巴赫约 +2.1%，肖邦约 +6.8%），导致：
- onset-only F1 仍保持中等（偶然邻近匹配）
- onset+pitch F1 暴跌到 0.0475/0.0534（邻近但不是同一个音符）
- 这制造了"旋律错音"的假象

按 MIDI tempo 元数据的精确比例恢复后，F1 完整恢复到 B 的水平。

### 6.4 关键工具与测试

| 工具 | 路径 | 作用 |
|------|------|------|
| `raw_midi_generator.py` | `work/transcription_benchmark/` | 生成 Transkun 原始 B MIDI（120 BPM 不变），产出 `notes_est.json` + `transkun_raw_120bpm.mid` + `run_manifest.json` |
| `diagnostic_evaluator.py` v2 | `work/transcription_benchmark/` | 诊断性评测器，分离 raw_metrics / diagnostic_metrics / error_buckets，支持全局 scale/offset 校准与局部对齐诊断 |
| `test_raw_midi_generator.py` | `tests/` | 真实推理验收测试（20 passed） |
| `test_diagnostic_evaluator.py` | `tests/` | v2 回归测试（50 passed），含 scale 恢复验证和白盒一致性断言 |

### 6.5 与旧诊断的冲突及更正

旧脚本 `diagnose_timing.py` 存在两个诊断错误：

1. **使用最后音符结束时间估算 scale**：受漏音和 note-off 误差影响，千分之一量级误差在长曲尾部累积超过 50ms。
2. **"P+Ons"字段取错**：实际读取了含 offset 约束的字段，却被当作无 offset 的 onset+pitch F1。

这导致旧报告声称校准后 F1 仅 0.3737/0.5408 — 该结论已被推翻。

### 6.6 项目决策

基于上述诊断，项目做出以下决策：

1. **B 的旋律音高不存在大规模错误**，不应以"修复旋律错误"为目标调整管线。
2. **主管线不得再对原始 MIDI 调用 `_fix_midi_tempo()`**。120 BPM 的 B 应作为不可变产物保存，评测统一使用 B。
3. **平均 BPM 覆盖导致的全局时间尺度变化是已接受的产品局限**，不要求修复。
4. **剩余研究重点转移**：从"修复音高"转为 **漏音、note-off/时值、踏板语义、帧级持续覆盖率**。
5. **后续评测统一使用 `diagnostic_evaluator.py` v2**，不再使用旧诊断脚本。
6. 负 pitch 事件（如 `pitch=-64`）是 Transkun 对 CC64 延音踏板的内部编码，不是模型生成非法音高。

### 6.7 Transkun 基于 Demucs piano stem 还是 source.wav 的评测

当前诊断基于现有 Demucs piano stem 重新推理。结论证明了 "C 的低 F1 由 tempo 覆盖引起"，但不能直接证明 Transkun 在任意混合编制 MP3 上同样具有 0.97+ F1。混合音乐仍需独立评估 Demucs 分轨质量。

### 8.2 中期（建议优先推进）

**P0：停止覆盖 Transkun 原始 MIDI（已完成诊断，待工程化）**

- `writeMidi()` 生成的 120 BPM MIDI（B）已证明编码了正确的音符事件和精度极高的时序
- 主管线 `audio_to_yaml_converter.py` 需改为保留 B 作为不可变产物，BPM 作为独立 sidecar 传递
- 如需生成带 BPM 的播放 MIDI，需同步重算 tick 以保持绝对时间不变，且不得覆盖原始 B

**P1：Transkun 剩余质量问题诊断**

tempo 问题消除后，剩余优化重点转移（按优先级排序）：

1. **肖邦漏音分类**：按力度、音区、局部复音密度统计漏音分布。当前肖邦 Recall=0.9475，需要确定漏音是高密度和弦、弱音、内声部还是低音。
2. **note-off/时值估计优化**：onset+pitch+offset F1 从 0.93/0.84 降至 0.94/0.84，offset P95 达 42-46ms。这是当前 B 与 A 之间最大的剩余差距。
3. **踏板语义（CC64）联合评测**：巴赫有 54 个 CC 事件、肖邦有 178 个。当前评测仅作音符级评测，未评估 CC64 对音符持续语义的影响。
4. **帧级持续覆盖率**：肖邦 frame accuracy 仅 0.6811，表明高密度段落的帧级覆盖有显著差距。
5. **Demucs 分轨与 source.wav 直送对比**：判断分轨是否损失弱音和持续音。

**P2：调性检测集成**（维持原有计划）
   - 当前 `score_semantic_analyzer.py` 实现了和声功能推断，但尚未集成全局调性检测
   - 引入调性上下文后，临时记号的拼写可以更加合理（例如 C# vs Db 的选择）
   - 可以基于 music21 的 `key.Key` 分析或 Krumhansl-Schmuckler 调性检测算法

**P3：专业参考谱对比验证**
- 技术方案中提到的"可选：用户本地专业参考谱验证"尚未实现
- 需要支持用户提供一份正式钢琴谱（MusicXML/PDF），与自动生成的五线谱做量化对比
- 这将大幅提升缩编质量的可信度

**P4：与 svsep_mpdr 管线的融合实验**
- svsep_mpdr 有 GNN 声部分离能力，而 score_aware_theory 目前使用基于音高的简单声部分配
- 二者可以互补：GNN 输出作为声部/谱表分配的参考信号，提升分配准确性

**P5：乐理精排替代方案验证**
- 现有 test_score_aware_theory_arrangement.py 中有对比测试框架
- 验证 score_aware_theory 在 MFCC/色度相似度等客观指标上是否追平或超越 attention_weighted
- 需对多首曲目（残酷天使、One Last Kiss、ただ声一つ、Beautiful World 等）进行批量对比

### 8.3 长期方向

1. **管线的"人类可审查"闭环**
   - 当前输出是 YAML（机器可读）和 MusicXML（人类可读）
   - 理想流程：自动生成 MusicXML → 人类审查 → 反馈修正 → 重新缩编

## 九、已知风险与未完成项

| Transkun CC 事件混淆 | 低 | 负 pitch 事件（如 `pitch=-64`）是 CC64 延音踏板编码，不是非法音高。评测和缩编管线需正确处理此类事件。 |
